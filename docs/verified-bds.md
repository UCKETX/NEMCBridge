# BDS 访客昵称核验与 OP 管理

## 昵称与身份

普通直连本机后端（`127.0.0.1`、`::1` 或 `localhost`）收到支持该功能的 FGAuth 签发的房间核验凭据后，桥接按已确认的访客 UID 查询网易档案，将核验的昵称设为 BDS 登录名。无需创建 `verified-bds.json`。不支持核验的 FGAuth 不会签发凭据，未绑定 OP 管理的普通房间保持 `NEMCB_<UID>` 稳定登录名；游戏内昵称显示是独立功能。核验失败不采信客户端自报昵称。不要用玩家名、兼容 XUID 或占位 UUID 作为授权凭据。

使用同一账号 UID 和同一世界时，背包对应的存档身份不随昵称改变。过去以其他身份生成的旧存档和旧 OP 记录不会自动迁移。群服互通插件若读取 BDS 的原生玩家名，即可读到核验昵称；如果插件读的是账号 ID 或旧日志，则行为由插件决定。不能把按昵称授予权限的插件混用到此模式。

## 分服授权（托管 BDS）

仅用于可信本机、直接连接的 BDS。限制离线 BDS 的入口为受信任的桥接，BDS 默认权限设为 member，关闭其他按名字授予 OP 的插件或控制流程。远程 BDS、自动转服和第三方面板的后台不在支持范围内。自建 FGAuth 需要部署支持访客昵称核验的版本；绑定下述 OP 管理时，缺少核验凭据会拒绝开房，不会以不核验的方式继续授予 OP。

1. 在 BDS 与桥接所在的支持 Unix 命名管道的系统上，由管理员准备 BDS 专用私有目录（`0700`）。下面用 `/run/bds-a/commands` 举例；在容器或 systemd 中，用实际服务账号可访问的路径，不能放在可由其他用户写入的位置。
2. 要让原后台的 `op` / `deop` 同步，运行安装包中的 `python3 scripts/bds-console-ingress.py /run/bds-a/commands --prepare`，然后将 BDS 的标准输入连接到配对的 `/run/bds-a/commands.engine`。把去掉 `--prepare` 的同一命令作为托管服务运行，后台继续向原来的 `/run/bds-a/commands` 输入。不要让启动脚本绕过适配器直接把授权命令写入 `.engine`。
3. 给 NEMCBridge 启动服务设置 `NEMCBRIDGE_BDS_CONSOLE_ENDPOINTS`，例如：

   ```json
   [{"upstream":"http://127.0.0.1:19453","fifo":"/run/bds-a/commands"}]
   ```

   地址要与管理台的国际服地址完全一致。多台 BDS 分别使用不同的管道和地址；桥接自动发现配对管道，无需手填套接字。此处是一次性服务配置，不是在每个房间内手改 JSON。
4. 打开管理台「国际服 → 对应卡片 → OP 授权」。已核验且在线的账号可以授予或撤销，已授权的离线账号也能在管理台撤销。后台命令用已核验的在线昵称选择目标，实际记录只保存该服的 UID；该后台命令不会猜测离线或跨服账号。桥接不可用时，适配器不会把 `op` / `deop` 原样放行。

先备份 BDS 世界及桥接数据目录，再改启动方式。现有从未托管的 BDS 不会被更新程序自动重启或改造。单测和实服验证边界见各版发行说明。
